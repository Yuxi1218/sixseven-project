# 給初學者的完整程式碼解析交接書

> 這本書是給**完全沒寫過程式**的隊友看的。
> 只要你會按手機、會開電腦，就能看懂本系統大概在做什麼。
> 建議順序：先看第 1 章理解全貌 → 再看各章解析 → 有不懂再看第 8 章詞彙表。

---

## 第 1 章 這套系統到底在做什麼（先看這章！)

想像我們在拍一支「飛機機翼傷痕檢查」的影片，只是檢查的不是人，而是一台**聰明的電腦**（NVIDIA Jetson 小型電腦主機）。

整個系統可以想像成一家「機翼健檢中心」：

```
     手機相機                    Jetson 主機(後台)                 手機螢幕
 ┌───────────┐    拍到的畫面     ┌───────────────┐   判斷結果      ┌───────────┐
 │ ①拍照/錄影  │ ──────────────→ │ ②用 AI 找損傷  │ ────────────→ │ ③顯示綠框  │
 └───────────┘    (WebRTC串流)  └───────────────┘   (DataChannel) └───────────┘
```

三步驟白話版：

1. **手機**把鏡頭看到的畫面「直接丟」給 Jetson（不經過中間手續，這叫 **DMA 式旁路**，後面會講）。
2. **Jetson** 用一個「受過訓練的 AI 模型」（叫 YOLO）在畫面上找有沒有損傷，找到就在心裡畫一個綠色的框。
3. **手機**收到「哪個位置有框」的座標後，在自己螢幕上把綠框畫出來 → 你看到的就是「AI 幫你把損傷框起來」。

重點：**畫面本身不傳回去**，只有「框的座標」傳回去，所以手機畫面超順、不會卡。

## 第 2 章 檔案總覽（誰負責什麼）

整支系統主要靠這 4 支程式配合，就像一家店的 4 個部門：

| 檔案 | 部門 | 白話說明 | 說的是哪種程式語言 |
|---|---|---|---|
| `webUI_workspace/main.py` | 總店長 | 管所有事情的主程式：開伺服器、載入 AI、處理請求 | Python（主機語言） |
| `webUI_workspace/webrtc_stream.py` | 水管工 | 專門負責「手機 ↔ 主機」之間的高速畫面水管 | Python（主機語言） |
| `webUI_workspace/static/app.js` | 手機前台 | 手機瀏覽器裡跑的邏輯：開相機、畫框、顯示報告 | JavaScript（手機語言） |
| `webUI_workspace/templates/index.html` | 手機牆面 | 手機畫面的「骨架」，決定面板長怎樣 | HTML（網頁標記） |
| `webUI_workspace/models/yolo11s.pt` | 老師傅 | 那個「受訓過的 AI」，真正的判斷專家 | AI 模型檔 |
| `deploy_watcher.py` | 自動送信兵 | 每 5 分鐘幫你「訓練完 → 自動換新模型」 | Python |

> 名詞小教室：`.py` = Python 檔，`.js` = JavaScript 檔，`.html` = 網頁結構檔，`.pt` = AI 模型的權重檔。
> 「後端/主機端」指 Jetson 主機，跑的 main.py、webrtc_stream.py；「前端/手機端」指瀏覽器，跑的 index.html、app.js。

## 第 3 章 main.py —— 總店長（最重要的主程式）

### 3.1 開頭設定（main.py:1~41）
- 主機一開機，先把要用的一堆「工具包」（OpenCV 影像處理、FastAPI 網頁伺服器、PyTorch AI 框架）都載入。
- `CONFIG` 是一張「設定表」，例如：AI 模型檔案放哪、信心門檻 0.25（低於 25% 就當作沒看到）、用哪顆 GPU。
- 特別一提：main.py:8~15 是在「允許 AI 檢查點檔案被讀取」。這是新版 PyTorch 的安全規定，不這樣寫模型就載不進來。

### 3.2 罪案偵測清單（main.py:43~53）
`CLASS_NAMES_ZH` 是「英文類別 → 中文名稱」的翻譯表：

| 英文 | 中文 |
|---|---|
| Crack | 裂痕 |
| Dent | 凹痕 |
| Missing_Fastener | 缺鉚釘 |
| Skin_Cover | 蒙皮受損 |
| Fuselage_damage | 機身損傷 |
| Wing_damage | 機翼損傷 |
| Engine_damage | 引擎損傷 |

這就是那 7 個類別。AI 判斷出其中一個，就會把對應中文顯示在框上面。

### 3.3 畫中文框的工法（main.py:62~83）
`_draw_zh_boxes()` 這支小工法負責「把綠框和中文標籤畫上去」：
1. 因為 OpenCV 原本不支援中文字，所以先把圖片「借」給 PIL（另一個繪圖工具）來畫。
2. 每個偵測到框畫一個綠色矩形 + 綠色底的黑字標籤（例如「裂痕 87%」）。
3. 畫完再轉回原格式顯示。

### 3.4 模型管家 YOLOManager（main.py:85~276）
這是整個系統的「心臟」。它是一個「管理 AI 模型的櫃子」，用兩個關鍵 call 服務：

- **`load_models()`（main.py:140~184）**：開機時執行。
  - 先檢查有沒 GPU（顯示卡），有就用 GPU 加速，沒有就退回 CPU。
  - 載入 7 類的新模型 `yolo11s.pt`。
  - **重要細節（main.py:173~175）**：串流用的 `model_n` 直接等於診斷用的 `model_s`，也就是**即時偵測也吃同一顆最新 7 類模型**，不再用舊的 nano 模型。
- **`infer()`（main.py:186~254）**：真正的「判斷」動作。
  - 吃進一張圖片 → 叫 YOLO 模型算一次 → 拿回所有框框（座標、信心值、類別）。
  - 用 `use_large=True` 決定用比較準的模型。
  - 算完後把結果記進 `current_frame` / `annotated_frame` 兩個「共用區」供其他功能取用。
- **`_update_fps()`（main.py:268~276）**：每秒算一次「目前畫面跑多快（FPS）」，顯示在手機上。

> 為什麼 AI 只會跑一次就有一堆框？因為一次 `predict()` 就會把所有損傷一次全列出，不用一張張檢查。

### 3.5 文字顧問 OllamaManager（main.py:279~359）
- 除了 AI 找框，系統還有一個「文字顧問」：Ollama（一個本地跑的小型 AI）。
- `generate_diagnosis()`：當偵測到「嚴重」損傷（機身/機翼/引擎損傷）時，會把偵測到的類別整理成一句話問 Ollama：「這是飛機維修專家，機翼檢查發現：裂痕。請給出嚴重程度與維修建議。」
- 結果只會顯示在「定格診斷」報告區。

### 3.6 網頁伺服器部分（main.py:366~447）
- main.py:366~379：FastAPI 起動時先載模型，起動完成前會印出模型狀態。
- main.py:384~389：一個「後台總閘門」中繼層，**禁止所有東西被手機快取**。這樣每次開網頁都是最新版，不會看到舊畫面。
- main.py:392~402：首頁 `/`：讀取 index.html，並把 js 版本號改成「最後修改時間」，確保瀏覽器一定拿新版（現場比賽免清快取）。
- main.py:405~411：`/status`：回報系統狀態（有沒有載入模型）。
- main.py:414~447：`/stream`：MJPEG 串流。如果只靠手機逐張傳太慢，這個是給沒走 WebRTC 時的備援；有新版畫面就送出，沒新版則短暫等待。

### 3.7 即時診斷核心（main.py:450~548）
這一段是「即時診斷」的開關設計：

- `_web_infer_loop()`（main.py:465~510）：一支**永遠在幕後跑的迴圈**。
  1. 等手機的「上游幀」到達（webrtc 模組給的）。
  2. 每到一幀就做一次 AI 判斷（main.py:488，用 `use_large=True`），約每幀 21 毫秒 = 每秒 45 張。
  3. 把偵測框**歸一化**（把座標除以寬高變成 0~1 的小數，這樣不管手機畫面多大都能對上）→ 推給手機（main.py:491~504）。
- `/webrtc/offer`（main.py:513~529）：手機進網頁按「即時診斷」時，主機會做兩件事：開一把與手機的「連線」（PeerConnection），並啟動 `_web_infer_loop`。
- `/webrtc/answer`（main.py:532~548）：手機把「回覆信號」交回主機，正式建立連線。

> 為什麼要這套 WebRTC？如果走傳統方式，手機會「一幀一幀→轉成照片→上傳→等回傳」，又慢又卡。WebRTC 是一次把「相機水管」直接接到主機，像把兩根水管接一起，水（畫面）直接流過去。

### 3.8 上傳與診斷 API（main.py:551~755）
- `/infer`（main.py:551~573）：手機把一張照片丟給主機做判斷，回傳「偵測框 + FPS」。
- `/infer_hd`（main.py:576~622）：**高清定格診斷**。重點是 main.py:592：同一張圖連跑 **3 次** AI，再把結果合併。這樣就算單次漏檢，3 次合併也能救回來，更穩。
- `/diagnose`（main.py:690~720）與 `/diagnose_upload`（main.py:723~755）：驚「嚴重損傷」時才啟動 Ollama 文字顧問；只有輕微缺陷時回傳固定提示「此影像僅偵測到輕微缺陷…」（main.py:642）。
- `/reconnect-wifi`（main.py:653~687）：測試用的小工具，把 WiFi 從主機熱點切回一般基地台（開發者用）。

### 3.9 主程式入口（main.py:758~781）
`python main.py --ssl` 啟動語法：
- `--ssl` 表示用 HTTPS（加密連線）。手機瀏覽器打開相機一定要安全來源，所以要加密。
- `--port 8000` 表示網頁掛在 8000 號連接埠。

## 第 4 章 webrtc_stream.py —— 水管工（串流模組）

### 4.1 這個檔在幹嘛
負責「手機 ↔ Jetson」之間的高速畫面水管。設計重點是 **DMA 式旁路**：手機鏡頭畫面**不逐張轉檔**，而是直接「旁路」送進主機——所以手機能維持高畫質高手速。

### 4.2 共用區與小工具（webrtc_stream.py:19~54）
- `_upstream_img`：手機最新一張相機畫面（會一直更新成最新，所以叫「最新」）。
- `_upstream_seq`：畫面編號，每來一幀 +1，避免重複處理。
- `init()`：設定「下游要送什麼畫面」的來源（就是總店長畫好的框圖）。
- `get_upstream_frame_newest()`：主程式拿「手機最新畫面」來做判斷。
- `push_detections()`：把偵測框資料（歸一化座標+標籤）廣播給手機的 data channel。

### 4.3 下游：把「框好的畫面」推給手機（webrtc_stream.py:56~95）
`AnnotatedFrameTrack`：負責把「已標框的畫面」編碼後送給手機顯示。
- `recv()`（webrtc_stream.py:67~95）:
  1. 以每秒 28 幀的節奏送（main 3 行），維持流暢。
  2. 若還沒圖就送黑畫面（所有像素 0）。
  3. 若上游解析度較小，就放大到 1280 寬（維持高畫質）。這裡是為了「畫質提升」，跟「位置偏移」完全是兩回事。
  4. **關鍵的一行（webrtc_stream.py:90）**：`img[:, :, ::-1]` 是把 RGB 顏色翻轉成 BGR——OpenCV 習慣用 BGR 表示顏色。還有 `np.ascontiguousarray` 讓記憶體連續，編碼才快。
  5. 設定正確的時間戳（pts / time_base）給瀏覽器的影像解碼器，否則畫面會全黑。

### 4.4 上游：接收手機相機畫面（webrtc_stream.py:98~116）
`_consume_upstream()`：幫「手機遞過來的相機畫面」接水。
- `frame.to_ndarray(format="rgb24")` 把視訊幀轉成可以被 OpenCV 處理的格式。
- `img[:, :, ::-1].copy()` 把 RGB 翻回 BGR 存進共用區（main 一行）。
- `_upstream_seq += 1` 登記新幀編號。

### 4.5 建立連線（webrtc_stream.py:129~201）
- `create_offer()`：主機準備一把「連線」：
  1. 建立 `RTCPeerConnection`（網頁即時通訊標準物件）。
  2. 加一條「下游」軌道（送框給手機）。
  3. 建立 data channel `"detections"`（送座標資料）。
  4. 登錄事件：手機送 track 來就開始接上游（`:146~150`）；斷線就清理（`:152~158`）。
  5. 等 ICE（找對方位址的機制）收集完，回傳完整 offer SDP（連線邀請函）。
- `set_answer()`：手機回覆「answer」後連線正式建立。
- 當所有連線關閉時，會通知主程式停掉幕後推理（`_notify_peer_closed`），釋放 GPU 給別的工作。

## 第 5 章 app.js —— 手機習慣燈控（前端邏輯）

### 5.1 開機（app.js:1~73）
- 網頁一載入就建一個 `WingDetectionApp`（機翼檢測 App）物件並初始化。
- `init()`：顯示「就緒」，自動開啟手機相機。

### 5.2 相機管理（app.js:88~145）
- `openCamera()`：跟手機要相機權限，並用 `facingMode: 'environment'`（後鏡頭）。
  後面故意用**後鏡頭**，因為要看機翼。
- `showLocalCamera()` / `showRemoteStream()`：切換畫面顯示模式——「才只有相機」或「有 AI 框」。

### 5.3 即時診斷開關（app.js:149~266）
- `toggleLive()`：按「啟用即時診斷」或「關閉即時診斷」。
- `startStreaming()`：建立與主機的連線：
  1. 把手機相機 track 全部加進連線（app.js:179~185）→ **上游**是手機畫面。
  2. 監聽 `ontrack`（app.js:188~216）：主機推回畫面就在 `remoteVideo` 顯示；並印出畫格狀態除錯。
  3. 監聽 `ondatachannel`（app.js:229~233）：收到座標資料就交給 `handleDetections` 畫框。
  4. 走信令流程：跟 `/webrtc/offer` 拿邀請 → 回 `/webrtc/answer`。
- **關鍵設計**（app.js:275~279）：畫框的對象「恆為本地相機」——也就是手機畫面是**原始的、不經壓縮的**，AI 框疊上去，所以又清晰又對位。

### 5.4 疊框對位科學（app.js:281~326）
這是「框會疊準」的秘訣，也是之前有 bug 的地方：

- `_coverRect()`（app.js:284~296）：用手機相機的畫面尺寸 & 螢幕容器尺寸，算出 `object-fit: cover` 的縮放後座標：`scale = max(寬比/高度比)`，再計算偏移 `ox/oy`。這樣不管手機直拍橫拍，框都對得上。
- `drawDetections()`（app.js:298~326）：
  - 把畫布清了重畫（`clearRect`）。
  - 用 `_coverRect` 的縮放把「歸一化座標」還原成螢幕像素。
  - 畫 3px 綠框 + 綠色底黑字標籤（例如「裂痕 87%」）。

### 5.5 資訊顯示與優化（app.js:328~362）
- `monitorStats()`：每秒抓連線統計，顯示 FPS；若 FPS 低於 12 顯示警告。
- `boostUpstream()`：連線後稍微延遲，把手機「送出解析度」提高成 1920x1440，真 HD 而非放大。

### 5.6 定格診斷（app.js:374~463）
- `startDiagnosis()` 三步走：
  1. 把目前相機畫面「凍結」成一張高清照片（`drawImage` 到 canvas → `toDataURL`）。
  2. 背景把照片 POST 到 `/infer_hd`（主機跑 3 次合併）。
  3. 把回傳的「框好圖」顯示，報告列出各損傷類別與信心。
- `resumeLive()`：看診完回到原本模式（即時診斷或相機）。

## 第 7 章 deploy_watcher.py —— 自動送信兵

這支程式獨立於網頁系統之外，是「自動部署」的關鍵。它由 cron（排程器）**每 5 分鐘**自動跑一次：

1. 連到訓練用的**筆電**（`192.168.0.111`）。
2. 看筆電上還有沒有「訓練程式」在跑（`ps aux | grep train_bal(_fast).py`）。
   - 有在跑 → 印「訓練中（proc=N）skip」，結束。
3. 訓練跑完 → 拿筆電裡 `best.pt`（最佳模型）的資訊（大小、時間）。
4. 跟主機上現役的 `yolo11s.pt` 比大小：
   - 一樣 → 代表已經部署過 → 寫一個 lock 檔防止再動，結束。
   - 不一樣 → 把筆電的 `best.pt` 下載回主機，覆蓋現役模型（`os.replace`）。
5. 重啟網頁服務（`start_webrtc.sh`），讓新模型「上線」。

> lock 檔（`/tmp/opencode/deployed.lock`）：一支「記號」檔。存在就代表部署完成了，之後每 5 分鐘的檢查都不會再亂動。

> 歷史教訓：先前 watcher 用了錯誤的 `c.stat()` 寫法（paramiko 沒有這個方法），導致它誤判「模型不存在」而沒部署，卡了一整天沒更新。**修改 2026-09-08**：改成正確的 `sftp.stat()`，部署功能已恢復並驗證。

## 第 8 章 詞彙表（有不懂就來查）

| 詞 | 白話解釋 |
|---|---|
| **AI 模型 / YOLO** | 一個「被大量照片訓練過」的程式，能在一張圖裡找出物件框。yolo11s 是較準的版本。 |
| **權重檔 (.pt)** | AI 訓練完的「記憶檔」，存著所有學到的判斷知識。 |
| **推理 / infer** | AI 拿一張圖「算一次」找損傷的動作。 |
| **偵測框 (bbox)** | AI 找到損傷位置，回傳的矩形座標 [x1,y1,x2,y2]。 |
| **信心值 (confidence)** | AI 相信自己找到它有多高（0~1），例如 0.87 = 87%。 |
| **歸一化座標** | 把座標除以畫面寬高，變成 0~1 比例。手機顯示時再乘回螢幕尺寸，就不怕解析度不同。 |
| **FPS** | 每秒幾張畫面，越高越順；<12 會警告。 |

## 第 9 章 眾人常問的「為什麼」

1. **為什麼畫面不直接由主機推回來？**
   → 手機畫面是高畫質原始畫面；若主機壓縮推回，會卡會糊。所以我們只傳「框座標」回來，畫面留在手機自己畫。

2. **為什麼疊框會「對不準」（歷史 bug）？**
   → 之前把「解析度提升/顏色翻轉」等處理混進上游消費，導致座標與畫面錯位。修正後：上游只負責「收幀 + 轉 BGR」，不亂動座標。

3. **為什麼定格診斷比較穩？**
   → 因為同一張圖會跑 **3 次**再合併（main.py:592），漏檢機率大大降低。

4. **為什麼看直播時有時看不到「多個損傷」？**
   → 兩個模式都吃同一顆模型。看不到通常**不是顯示 bug**，而是模型沒偵測到（尤其小樣本類別，如缺鉚釘）。

5. **為什麼要 HTTPS（網址開頭是 https://）？**
   → 手機瀏覽器政策：非 HTTPS 不給開相機。所以主機自簽憑證提供 HTTPS。

6. **為什麼 index.html / app.js 掛 `?v=15`/`?v=修改時間`？**
   → 強制瀏覽器載入最新版，現場評審的手機不會看到舊畫面（Cache-Control no-store 也一併保證）。

7. **兩個模型 yolo11n 跟 yolo11s 差在哪？**
   → s 比較大、比較準、比較慢；n 比較小比較快。目前**兩個實際上都是同一顆**（main.py:173~175 共用），以準度為優先。

## 第 10 章 快速查詢：常見「流水線」

**即時診斷流水線（Live）**
```
手機 openCamera → 按「啟用即時診斷」→ startStreaming
  → GET /webrtc/offer → 主機啟動 _web_infer_loop
  → 手機送相機 track（上游）→ _consume_upstream 收幀 → 存 _upstream_img
  → _web_infer_loop 拿最新幀 → yolo_manager.infer(use_large=True)
  → 偵測框歸一化 → push_detections → DataChannel → app.js handleDetections
  → drawDetections（_coverRect 算縮放）→ 手機螢幕畫綠框
```

**定格診斷流水線（Snapshot）**
```
按「開始診斷」→ 凍結畫面相 → POST /infer_hd
  → 主機得分 _decode_image → infer×3 → 合併偵測框 → 畫中文框 → 回 base64 圖片
  → app.js 顯示框好的圖 + 報告 → 按「繼續拍攝」回原模式
```

**自動部署流水線（Watcher）**
```
cron 每5分鐘 → deploy_watcher.py → SSH 連筆電
  → 檢查 train_bal*.py 是否還在跑 → 跑完則取 best.pt 資訊
  → 比對現役 yolo11s.pt 大小 → 不同則下載覆蓋 → 重啟服務 → 寫 lock
```
